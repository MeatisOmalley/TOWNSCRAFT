# DOScraft / 86Box performance-fidelity audit — 2026-10-11

Scope: the historical 86Box v6.0 Windows executable (`dc236a27…e885`), the DOScraft 486/ET4000 diagnostic profile, and the local 86Box v6.0 source. During this audit, another worker completed a locally patched runtime (`bd6d874b…2031`, source commit `079bc829…3632`) for the 32-bit-to-16-bit VGA write charge, and changed the profile to 33 MHz. This audit does not modify or benchmark that runtime. Previously published 25 MHz frame times must not be compared directly to future 33 MHz results. The VGA dword-write charge is excluded from the ranking below.

**Update after this audit (2026-10-11):** the patched runtime was benchmarked against the official one at 33 MHz and every Low frame, stage and upload mean was identical (see [PERFORMANCE.md](PERFORMANCE.md)). The dword-split charge does not set the emulated upload cost in this configuration, so rows that assume a fixed VGA charge (#3, #5) describe the timing table, not the observed ~1.6 µs per uploaded dword. Follow-up: the real cause was that v6.0 registers the ET4000AX ISA as an 8-bit card (byte-only handlers). The DOScraft runtime fixes that and runs an 11.1 MHz ISA bus; upload fell 12.9 -> 5.3 ms (see PERFORMANCE.md).

## Finding that affects the June 30, 1990 hardware cutoff

The selected system ROM contains three copies of `05/05/91`; the selected ET4000 V8.06 ROM contains `04/15/92` (two copies). These dates come from the exact ROM binaries pinned by [the VM launcher](tools/run_vm.py), not file modification dates. The CPU and ET4000 controller can still be period-correct: [Intel lists the 486DX family](https://www.intel.com/pressroom/kits/quickreffam.htm), [ASUS places ISA-486 in 1990](https://www.asus.com/event/pcdiy/sg/our-legacy.html), and [Tseng's ET4000 data book is dated 1990](https://www.dosdays.co.uk/media/tsenglabs/Tseng_Labs_ET4000_Graphics_Controller_1990.pdf). But these *firmware revisions* are outside the cutoff, and the ASUS board's pre-July availability has not been established. BIOS setup can change cache, memory and video-register state, so this is also a possible performance confound. A valid period baseline needs a verified pre-July board/ROM pair and video ROM, or an explicit decision that later firmware is allowed for a period-correct chip. Do not silently relabel the current VM as a June 1990 system.

## Ranked timing risks beyond the VGA dword-write bug

| Priority | Mechanism and evidence | Likely bias in DOScraft | Confidence / bounded test |
| --- | --- | --- | --- |
| **1** | **486 cache and RAM access are not modeled by cache-line hits/misses.** [The CPU table](../86Box-v6.0-timing/src/cpu/cpu_table.c) gives DX/33 fixed main-memory reads/writes of 6 cycles and external-cache reads/writes of 3. [CPU wait-state selection](../86Box-v6.0-timing/src/cpu/cpu.c) disables the prefetch model when internal cache is enabled; [the interpreter](../86Box-v6.0-timing/src/cpu/386.c) invokes prefetch accounting only when that model is active. No 8 KiB instruction/data tag capacity, line fill, or conflict behavior is present in these paths. Intel's [1990 hardware manual](https://www.bitsavers.org/components/intel/80486/1990_i486_Microprocessor_Hardware_Reference_Manual.pdf) describes an 8 KiB on-chip cache, write-through behavior and nonzero miss/fill costs. | **Can help** the emulator on large/shifting renderer code, shaded textures and framebuffer data by omitting misses and external RAM traffic. Fixed instruction costs can simultaneously hurt some cache-hit sequences. This is the largest uncalibrated CPU-side risk, potentially many milliseconds in dense scenes, but no signed net estimate is justified yet. | High that the model is simplified; low on net direction/magnitude. Trace guest CR0 and SiS cache-enable state, then compare cache-sensitive DOS microbenchmarks (small vs >8 KiB code/data, streaming writes) on this VM and a real DX/33 with documented L2/RAM. A simple cache-off A/B is a sensitivity test, not a real-cache simulation. |
| **2** | **Hot integer multiply timing is fixed, while the real 486 varies by operand.** [The interpreter](../86Box-v6.0-timing/src/cpu/x86_ops_mul.h) charges 30 clocks for 32-bit two-operand `IMUL` and 25 for immediate form, irrespective of value. Intel's [1989 i486 data sheet, instruction clock table](https://www.dosdays.co.uk/media/intel/i486_Data_Sheet_Apr89.pdf) lists a 13–42-clock range for 32-bit signed multiplication. Division is similarly a fixed charge in [F7 arithmetic](../86Box-v6.0-timing/src/cpu/x86_ops_misc.h). DOScraft's row setup uses repeated multiplies and its draw profile attributes 15–26% of draw time to row setup. | **Can hurt or help.** Small multipliers may execute faster on real silicon than the fixed 30 clocks; other operands may be slower. A 10-clock error across thousands of row multiplies would be on the order of milliseconds, especially looking down. This is a sensitivity illustration, not a measured correction. | High that fixed timing differs from operand-dependent hardware; medium that it matters to this renderer. Count `IMUL`/`IDIV` by opcode and operand distribution in still/walk/down, then replay exact hot-loop microbenchmarks on real DX/33 or a calibrated hardware trace. |
| **3** | **ET4000 access timing remains a single fixed table after the dword split is fixed.** [The ET4000 model](../86Box-v6.0-timing/src/video/vid_et4000.c) assigns 3 ISA clocks to byte/word writes, 6 to dword writes, and fixed read costs. [The SVGA write handler](../86Box-v6.0-timing/src/video/vid_svga.c) charges that value without a scanout/FIFO/DRAM-state term. Tseng's [1990 data book](https://www.dosdays.co.uk/media/tsenglabs/Tseng_Labs_ET4000_Graphics_Controller_1990.pdf) describes a FIFO/cache/memory arbitrator, and says zero-wait writes are feasible under stated board and memory conditions. | **Either direction**, board-dependent. A good zero-wait board may match the fixed 3-clock assumption; a slow board or saturated FIFO may be slower. After the dword fix, the current 13 ms historical upload number is no longer the right starting point. | High on simplified timing; low on actual ET4000 board behavior. Measure byte/word/dword throughput on a dated physical ET4000 ISA board, during active display and blanking, with exact access pattern and 8 MHz ISA clock. Record board DRAM speed and wait-state jumpers. |
| **4** | **The generic HDD is not the proposed drive, and mechanical latency uses an average.** [The configured preset](../86Box-v6.0-timing/src/disk/hdd.c) is 3500 RPM, one 16-sector read-cache segment, 64-sector write cache, 8 ms track seek and 40 ms full stroke. Seek timing uses half a revolution for nonsequential reads rather than tracking actual rotational phase. | **Can help or hurt** loading/streaming and worst-frame tails. It has little reason to change fully resident raster loops. A real pre-July-1990 drive/controller pair could be faster or slower than this proxy; cache behavior is especially uncertain. | High that it is a proxy. Identify a dated drive and ESDI/SCSI controller, match its geometry/cache/seek specs, then measure cold loading, chunk streaming and edit/save tails separately from steady frames. |
| **5** | **ISA clock conversion is coarse.** DX/33 has `atclk_div=4` in [the CPU table](../86Box-v6.0-timing/src/cpu/cpu_table.c), while the default ISA speed is 8 MHz in [CPU setup](../86Box-v6.0-timing/src/cpu/cpu.c). `ISA_CYCLES(x)` uses the integer divisor and [video timing](../86Box-v6.0-timing/src/video/video.c) multiplies by it. Thus 6 modeled ISA clocks become 24 CPU cycles = 0.720 µs at 33⅓ MHz, versus 0.750 µs at exactly 8 MHz. | **Helps** the emulated VGA path by about 4% under that exact 8 MHz assumption—roughly 0.5 ms for 16,000 dword transfers. Actual board ISA frequency may differ, so this is not a measured correction. | High on arithmetic, medium on board clock. Log the effective 86Box ISA frequency after BIOS setup, and verify the target board's divisor/oscillator. |
| **6** | **AT DRAM refresh does not visibly steal CPU bus time in this path.** [AT PIT refresh](../86Box-v6.0-timing/src/pit.c) toggles a PPI bit; the XT path invokes a DMA read, but this AT callback does not charge CPU cycles. | Likely a **small favorable** bias for RAM-heavy code; exact size depends on chipset refresh policy and cache. Lower priority than cache and multiply timing. | Medium. Inspect SiS-specific refresh behavior and compare a memory-stream microbenchmark with real hardware; do not add a generic penalty without that evidence. |

## Measurement-model caveats, distinct from emulator bugs

- The published [Low replay](tests/benchmarks/2026-10-11/low-planar-low.json) is a **25 MHz**, frozen-simulation, silent-audio benchmark. Those choices make total frame time look better than a busy live world with Sound Blaster interrupts, while making scene-to-scene graphics comparisons more reproducible. They are not 86Box defects. Re-run the same route with live simulation/audio when judging actual play.
- `time_sync = disabled` and the game's PIT-based guest timer mean host fast-forward or host slowness does not by itself change a reported *emulated* millisecond. The CPU/device cycle model above is what can make those guest milliseconds unlike real hardware. The zero retrace-wait baseline also makes exact vblank phase a correctness/tearing question more than a current mean-frame-time issue.
- The current VM pins the interpreter (`cpu_use_dynarec=0`) and softfloat FPU. This avoids two common accuracy shortcuts, but does not supply cache or board-level cycle accuracy.

## Best validation order

1. Let the 33 MHz CPU and VGA-write work finish, then freeze executable, ROM, profile, game build and route hashes. Establish a new 33 MHz baseline; do not merge it with the old 25 MHz series.
2. Verify the target board and video ROM dates against June 30, 1990. Preserve the current VM as a separate later-firmware comparison.
3. Run tiny guest microbenchmarks for cached hot code, >8 KiB code/data, streaming framebuffer writes, `IMUL` operand classes and VGA byte/word/dword writes. Prefer at least one physical 486DX/33 + ET4000 board for calibration; without it, report *sensitivity ranges*, not corrected FPS.
4. Only then rerun DOScraft still/walk/down and disk-heavy tails. Attribute changes to CPU, cache, VGA bus and storage separately; inspect visual hashes and retrace behavior.
